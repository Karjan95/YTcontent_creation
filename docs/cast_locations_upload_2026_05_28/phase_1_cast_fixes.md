# Phase 1 — Cast Bug Fixes

**Created:** 2026-05-28
**Status:** Planned
**Estimated scope:** Frontend only. ~80 lines changed across one file.

## Context

The cast feature has two functional bugs and one misleading UI field, all surfaced during user testing:

1. **Regenerate ignores Visual Identity edits.** User edits the Visual Identity textarea on a cast card, clicks Generate, gets the same character back. The regen path sends a stale prompt that was baked at suggest-cast time.
2. **Every character ref box auto-checks per scene.** Scenes with zero cast members visible still render with all character portraits ticked, which causes scene generation to send irrelevant character refs and contaminate the image.
3. **"Appears in Beats" field is misleading.** It is an LLM guess from the narration that drives nothing — the actual per-shot character presence is derived from the production table's `character_outfit` text. Keeping the field encourages users to trust a value that has no effect.

Phase 1 fixes all three on the frontend. No schema changes, no backend changes.

## Scope

**In scope**
- `generatePortraitForCharacter` and `generateAllPortraits` rebuild the portrait prompt from the current Visual Identity text on every call.
- Per-scene character checkbox rendering and per-scene generation request both treat `selectedCharacters = []` as "no character refs for this shot" rather than "all".
- "Appears in Beats" is removed from the cast card UI and from `readCastFromUI` parsing.

**Out of scope**
- Backend changes to `/api/suggest-cast` (the `appears_in_beats` field can still come back in the LLM response — we just stop displaying and using it).
- New endpoints.
- Locations or upload support (Phases 2 and 3).

## Detailed changes

All changes are in `ui/index.html`.

### Fix 1.1 — Regenerate uses edited Visual Identity

**Where:** `generatePortraitForCharacter` (currently around line 7007-7069) and `generateAllPortraits` (currently around line 7071-7145).

**Current bug:**
```js
const prompts = char.portrait_prompts;
const refPrompt = prompts?.reference_sheet || prompts?.face_closeup;
```
`portrait_prompts.reference_sheet` is generated by Gemini at suggest-cast time using the original `visual_identity` (see `execution/research_templates.py:4300-4311`). User edits to `visual_identity` don't propagate.

**Fix:** Build the portrait prompt in JS from the current state:

```js
function buildReferenceSheetPrompt(char, styleSummary) {
    const stylePrefix = styleSummary ? `${styleSummary}. ` : '';
    const identity = (char.visual_identity || '').trim();
    return `${stylePrefix}Create a professional character reference sheet for ${char.name}: ${identity}. ` +
        `Use a clean, neutral plain background. Arrange in two horizontal rows: ` +
        `Top row: four full-body standing views side-by-side — front view, left profile (facing left), right profile (facing right), back view. ` +
        `Bottom row: three highly detailed close-up portraits — front portrait, left profile (facing left), right profile (facing right). ` +
        `Maintain perfect identity consistency. Relaxed A-pose, consistent scale. Even spacing, clean panel separation. Consistent lighting. Crisp, print-ready.`;
}
```

Replace the `refPrompt` lookup in both `generatePortraitForCharacter` and `generateAllPortraits` with `buildReferenceSheetPrompt(char, approvedStyle?.style_summary || '')`.

The layout template is lifted directly from `execution/research_templates.py:4300-4311` so the result matches what suggest-cast produces — but with the current `visual_identity` text.

Drop the "No portrait prompt available. Re-suggest cast to generate prompts." guard, since the prompt is always derivable now.

### Fix 1.2 — Empty selectedCharacters = none checked

**Where 1:** Per-scene checkbox rendering, currently around line 8749-8770.

**Current bug:**
```js
${(!s.selectedCharacters || s.selectedCharacters.length === 0 || s.selectedCharacters.includes(ch.name)) ? 'checked' : ''}
```
Empty array is interpreted as "all checked".

**Fix:** Strict membership only:
```js
${s.selectedCharacters?.includes(ch.name) ? 'checked' : ''}
```

**Where 2:** Header label on the same block (line 8752-8755).

**Current:**
```js
<span class="scene-chars-label">Characters: ${s.selectedCharacters && s.selectedCharacters.length > 0
    ? s.selectedCharacters.join(', ')
    : 'All (' + visualsCharacters.length + ')'
}</span>
```

**Fix:** Show `None` for empty:
```js
<span class="scene-chars-label">Characters: ${s.selectedCharacters && s.selectedCharacters.length > 0
    ? s.selectedCharacters.join(', ')
    : 'None'
}</span>
```

**Where 3:** Generation request character resolution, currently around line 8647-8661 (`getStructuredCharacters` / the function feeding `selectedCharacters` into the scene image request).

Find every site that does `if (scene.selectedCharacters.length === 0) return visualsCharacters` (treating empty as all) and change to `return []` (treating empty as none).

**Where 4:** Toggle handler that clears `selectedCharacters` when "all" gets selected (currently around line 9002-9013):
```js
if (scene.selectedCharacters.length === visualsCharacters.length) {
    scene.selectedCharacters = [];
}
```
This was the "all checked → reset to empty as shorthand" trick. **Remove this block.** With the new semantic, empty means none, not all.

### Fix 1.3 — Remove "Appears in Beats" field

**Where 1:** Cast card render, currently around line 6867-6871:
```html
<div class="cast-card-field">
    <label>Appears in Beats</label>
    <input type="text" class="cast-field-input" value="${...}"
           placeholder="..." data-field="appears_in_beats" data-index="${idx}">
</div>
```
**Remove this entire block.**

**Where 2:** `readCastFromUI`, currently around line 6927-6962. Remove:
- `const getBeatsStr = card.querySelector('[data-field="appears_in_beats"]')?.value || '';`
- `const beats = getBeatsStr.split(',').map(s => parseInt(s.trim())).filter(n => !isNaN(n));`
- `appears_in_beats: beats,` in the pushed object

**Where 3:** `addCastMember`, currently around line 6903-6916. Remove the `appears_in_beats: []` line from the new-character defaults.

**Where 4:** Keep accepting `appears_in_beats` in incoming data from `/api/suggest-cast` (don't crash if backend still sends it) — just don't render or persist it on the project doc. To enforce that, in `gatherProjectState` (around line 11994-12110) where `cast_data: currentCast || null` is written, optionally strip `appears_in_beats` from each cast member before save.

The backend `build_cast_suggestion_prompt` (`research_templates.py:4287-4370+`) can still ask for the field; this phase doesn't touch the prompt. Phase 2 can clean it up alongside the locations changes.

## Verification

1. Open an existing project with cast already defined.
2. Edit one character's Visual Identity (e.g. change wardrobe color from blue to red).
3. Click Generate / Regenerate on that character's portrait.
4. Confirm the new reference sheet reflects the new color. ✅ Fix 1.1
5. Open Visuals tab. Find a scene where the production table's `character_outfit` says "N/A — no characters in shot" or doesn't name any cast member. Expand the Characters selector for that scene.
6. Confirm zero character boxes are checked. Header reads "Characters: None". ✅ Fix 1.2
7. Generate that scene's image. Confirm no character reference is sent (check network tab for the request body; `characters` should be empty).
8. Find a scene with one named character. Confirm only that one box is checked and the generated image uses only that character's portrait.
9. Open a cast card. Confirm there is no "Appears in Beats" field. ✅ Fix 1.3
10. Suggest cast for a new project. Confirm cards render without the field even though backend may still return `appears_in_beats`.

## Risk and rollback

- All changes are isolated to `ui/index.html`. Rollback = revert that file.
- No data migration. Existing saved cast data with `appears_in_beats` will be ignored; new saves can optionally strip the field. Either way, no breakage.
- The portrait prompt template is duplicated between Python (suggest-cast) and JS (regen) — see Phase 2 for an opportunity to centralize, but not required.
