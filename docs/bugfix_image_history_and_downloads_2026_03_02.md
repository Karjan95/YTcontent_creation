# Bugfix: Image History Visibility & "Download All" Proxy — 2026-03-02

## Summary
Resolved two critical issues preventing users from accessing previously generated images and using the "Download All Images" functionality. The fixes involved patching URL validation logic and correcting per-scene filename prefixing.

---

## 1. "Download All Images" — SSRF Validation Fix

### Problem
When clicking **Download All Images**, the application failed to proxy signed URLs from Firebase Storage. The server logs showed:
`ValueError: URL domain not allowed: content-creation-app-staging.appspot.com.storage.googleapis.com`

### Root Cause
The `validate_url` helper in `server.py` (implemented for SSRF protection) used a strict equality check against an allowlist: `{'storage.googleapis.com', 'firebasestorage.googleapis.com'}`. Signed URLs generated by the Google Cloud Storage library often use the bucket name as a subdomain (e.g., `bucket.storage.googleapis.com`), which triggered a validation failure.

### Fix
Updated `validate_url` in `server.py` to allow any subdomain of the trusted storage domains. It now checks if the hostname matches exactly or ends with `.storage.googleapis.com` / `.firebasestorage.googleapis.com`.

**File modified:** `execution/server.py`

---

## 2. Image History Visibility — Double Prefix Fix

### Problem
Previously generated images were not appearing in the "Previous versions" history strip for each scene. Users reported that even after multiple generations, the history remained empty.

### Root Cause
A mismatch in how scene IDs were handled between the UI and backend:
1. The UI recently starting passing scene IDs that already included the `scene_` prefix (e.g., `"scene_1"` instead of `"1"`).
2. The backend history endpoint was hardcoded to prepend `scene_` to every ID, resulting in a search for `scene_scene_1_`.
3. Actual files in Firebase Storage were named `scene_1_TIMESTAMP.png`, so the double-prefixed search returned zero results.

### Fixes
- **Backend Fetching:** Updated the `/api/visuals/scene-image-history` route in `server.py` to check if a scene ID already starts with `scene_` before prepending. This ensures it finds existing `scene_1_` blobs correctly.
- **Backend Generation:** Updated `generate_scene_image` in `gemini_client.py` to check for the `scene_` prefix when saving new images. This prevents creating new files with `scene_scene_` names.

**Files modified:**
- `execution/server.py`
- `execution/gemini_client.py`
